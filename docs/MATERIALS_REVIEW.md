## Top 5 problems

1. **Textures render at 256² regardless of array class (#12, S2)** — the headline quality claim of the design doc (512²/1024² resident detail) is not what ships; every imported texture is downsampled to 256² and upscaled.
2. **Default workspace build is broken (#20, S2)** — `cargo test --workspace` cannot compile without `--features cindral-app/kernel-benchmark`; the strict completion check in AGENTS.md cannot pass on a clean checkout.
3. **Unbounded aggregate decode memory (#13, S2)** — up to 32.5 GiB transient with many large textures on a shared-RAM iGPU; failure mode is an OOM kill of the whole app (unsaved work).
4. **Export V-axis mismatch (#14, S2)** — OBJ and DAE exports show textures vertically mirrored versus the viewport in convention-respecting consumers; glTF is correct.
5. **Mapping size fields undo-flood (#3/#11, S3)** — one undo entry per keystroke with garbage intermediate values; plus Select-users missing component-interior/instance users (#6).

## Not verified here, and how to verify by hand

- **Swatch == viewport == export pixel for a palette-material face**: only viewport==export parity (legacy color) and the CPU-side table value are proven. Hand-check: paint a face a solid material, export PNG, and compare the face's pixel RGB with the swatch in an image editor.
- **Real 5,000-material frame time and the 2,000-file scan cap**: both tests are `#[ignore]` (slow/release). Run `cargo test -p cindral-app --release --features kernel-benchmark -- --ignored materials_panel_5000` and `scan_is_capped_at_2000_files`.
- **Behavior at the 127-asset limit on the GPU** (real allocation, no device loss) and memory pressure on Vega 11: needs a document with 127 embedded textures; the error-path code was read, not exercised on GPU.
- **Old real-world v1/v2 files looking identical**: fixtures were cross-checked against the historical writer, but no genuine pre-materials document was available to load.
- **Builtin name originality**: no trademark/branding references and no embedded assets (verified by grep), but provenance of the *style* of the collection can't be proven from code alone.

## Doc claims that were wrong

- `TEXTURE_DESIGN.md`: "the GPU resident copy is one 512² layer ≈ 1.33 MiB … Upload = resample to L plus a 10-level mip chain" — actually 256² (code caps at `resize_preview_256` before the array edge resample).
- `TEXTURE_DESIGN.md:44-50`: "L = 1024 while the document has ≤ 31 assets" — code gives L=1024 for ≤ 33 (34 layers × 5.59 MiB = 190.1 MiB ≤ 192); the table's "1024 → 31 layers fit" and MATERIALS.md's "31 layers at 1024² ≈ 170.7 MiB" are arithmetically wrong (31 layers at 1024² = 173.4 MiB; 34 fit).
- "anisotropy clamped to what the adapter reports" — hardcoded 16 (wgpu clamps internally, so harmless, but the claim is false as stated).
- `MATERIALS.md:66`: Ctrl+click "Fill the clicked face plus all connected adjacent faces" — omits "sharing the clicked face's material" (the code and the app's own hint are correct).
- `MATERIALS.md:38`: usage count described as "number of faces" — painted instances are also counted; `MATERIALS.md:78`: "cursor swatch" is a header swatch next to the tool options, not attached to the pointer.
- Framing note: the storage design is a single uniform array with an adaptive edge length (1024/512), not "size-class arrays (1024/512/256)"; the docs themselves are consistent on this, but the milestone's requirement wording is not.
